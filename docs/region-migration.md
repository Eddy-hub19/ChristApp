# Один регион для Render и Neon: план переноса

Цель: сервер Render и база Neon в одном регионе (лучше Франкфурт, `eu-central-1` — ближе всего к Украине), RTT до БД в простое с ~94 мс до 1–3 мс.
**Ничего из этого не выполнялось на проде.** Документ — пошаговый план; каждый шаг обратим до момента переключения `DATABASE_URL`.

## 0. Что известно сейчас

| Что | Значение | Откуда |
|---|---|---|
| Регион Neon | **us-east-1** (AWS, Вирджиния) | хост в `DATABASE_URL`: `ep-…​.us-east-1.aws.neon.tech` |
| Пулер Neon | **не используется** (в хосте нет `-pooler`) | тот же хост |
| Регион Render | **неизвестен из кода**: Render не отдаёт регион в переменных окружения ([список переменных](https://render.com/docs/environment-variables)) | смотреть вручную, см. ниже |

**Где посмотреть регион Render:** Dashboard → ваш сервис → **Settings** → блок **Region** (также виден на странице сервиса рядом с названием). Через API: `GET https://api.render.com/v1/services/<RENDER_SERVICE_ID>` → поле `serviceDetails.region`.
Найденное значение задайте в Render как переменную `RENDER_REGION` (`oregon`, `ohio`, `virginia`, `frankfurt`, `singapore`) — админ-панель «Процессы» покажет регион сервера рядом с регионом БД и предупредит, если они различаются. На работу сервера эта переменная не влияет.

**Как проверить результат:** админ-панель → «Процессы» → «База данных» → кнопка **«Замерить RTT»** (50 × `SELECT 1` на одном соединении; медиана и p95). Ориентиры: один регион 1–5 мс, соседние 20–30 мс, разные континенты 90+ мс. Если RTT ≈ 90 мс — Render, скорее всего, не в `us-east-1`/Вирджинии (внутри одного региона он был бы единицами мс).

## 1. Выбор схемы

Регион существующего Neon-проекта и существующего сервиса Render **изменить нельзя** — нужен новый проект/сервис в нужном регионе.

| Регион Render сейчас | Что переносить |
|---|---|
| Frankfurt | только **Neon** → `eu-central-1` (шаги 2–6) |
| Любой другой | **оба** (рекомендуется): Neon → Frankfurt и новый сервис Render в Frankfurt; либо только Neon в регион Render, если Frankfurt не нужен |
| Virginia | ничего не переносить для RTT; RTT должен быть единицами мс — ищите причину в другом (пулер, прогрев Neon) |

Оценка для пользователей из Украины: до Франкфурта ~35–50 мс против ~120–150 мс до США — выигрыш и для WebSocket-игр.

## 2. Подготовка (без простоя)

1. **Версии.** `pg_dump` должен быть той же или новее мажорной версии Postgres на источнике. Узнать: `psql "$OLD_DIRECT_URL" -c 'show server_version'`.
2. **Новый проект Neon в Франкфурте.** Console → *New project* → Region **AWS Europe (Frankfurt) eu-central-1**, ту же версию Postgres. Название: `christapp-fra`.
3. **Две строки подключения нового проекта** (Connect → переключатель *Pooled connection*):
   - `NEW_DIRECT_URL` — прямая (хост **без** `-pooler`): для миграций и `pg_dump/pg_restore`;
   - `NEW_POOLED_URL` — пулерная (хост **с** `-pooler`): для приложения (`DATABASE_URL`).
4. **Репетиция на копии** (можно сколько угодно раз, прод не трогает):
   ```bash
   # источник: ПРЯМАЯ строка старой базы (не пулер!)
   pg_dump "$OLD_DIRECT_URL" --format=custom --no-owner --no-acl --file=christapp.dump
   pg_restore --no-owner --no-acl --dbname="$NEW_DIRECT_URL" --jobs=4 christapp.dump
   ```
   Замерьте, сколько это длится — это и есть длительность окна простоя на шаге 4.
5. **Проверка копии** (шаг 5 ниже) — на репетиции тоже. Перед боевым прогоном новую БД очистите (удалить и создать ветку/базу заново), чтобы не смешать данные.
6. Если приложение будет ходить через пулер, а `prisma migrate` — напрямую: в `backend/prisma.config.ts` уже поддержана переменная **`DIRECT_URL`** (если задана, Prisma CLI берёт её; без неё всё как раньше). Приложение всегда берёт подключение из `DATABASE_URL`.

## 3. Параметры пула под 0.5 CPU

В Prisma 7 с драйвер-адаптером `connection_limit` и `pool_timeout` из URL **не действуют** — пул — это `pg.Pool` в `PrismaService`. Настраивается переменными окружения (значения по умолчанию уже заложены в коде):

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `DB_POOL_MAX` | 10 | Достаточно: при RTT 2 мс одно соединение даёт сотни запросов/с. При пулере Neon лимит клиентских соединений велик, но не нужен. Можно снизить до 5–6, чтобы меньше памяти/сокетов на 512 МБ |
| `DB_POOL_CONNECT_TIMEOUT_MS` | 10000 | Раньше ожидание соединения было бесконечным: при медленной БД очередь росла без ограничений (как «33 в очереди»). Теперь запрос падает через 10 с |
| `DB_POOL_IDLE_MS` | 30000 | Новое соединение (TCP + TLS + авторизация) стоит несколько RTT; 30 с вместо 10 с по умолчанию `pg` уменьшает «переподключения» в паузах |

Neon: при PgBouncer в режиме `transaction` не работают session-level возможности (`SET`, `LISTEN/NOTIFY`, `PREPARE`); `pg` использует неименованные подготовленные запросы, Prisma Client через адаптер работает с пулером. **Проверьте на копии** (шаг 2.4) — прогнать `npm run test` и сценарии чатов/кинотеатра; если что-то не работает через пулер, оставьте для приложения прямую строку.

## 4. Боевой перенос (окно простоя = время дампа + восстановления, обычно минуты)

1. Предупредить пользователей (баннер или сообщение в общем чате).
2. **Остановить запись:** в Render → сервис → **Suspend** (или временно выставить 0 инстансов). Так в старую БД ничего не запишется во время копирования. Клиенты покажут экран «сервер недоступен».
3. Свежий дамп и восстановление в **чистую** новую БД:
   ```bash
   pg_dump "$OLD_DIRECT_URL" --format=custom --no-owner --no-acl --file=final.dump
   pg_restore --no-owner --no-acl --dbname="$NEW_DIRECT_URL" --jobs=4 final.dump
   ```
   В дамп входит таблица `_prisma_migrations`, поэтому повторно накатывать миграции не нужно.
4. Если нужен **почти нулевой простой** — вместо дампа можно настроить логическую репликацию старой БД в новую и переключиться в момент, когда лаг нулевой. Это сложнее (нужны publication/subscription, проверка последовательностей) — сверьтесь с актуальной документацией Neon и репетируйте отдельно. Для приложения такого размера обычного дампа достаточно.

## 5. Проверка новой БД (до переключения)

```bash
# число строк в основных таблицах должно совпасть со старой БД
for t in User Message Room RoomMember RoomReadState Reaction WatchRoom WatchMessage PushSubscription RefreshSession; do
  echo -n "$t: "; psql "$OLD_DIRECT_URL" -Atc "select count(*) from \"$t\""
  echo -n "$t (new): "; psql "$NEW_DIRECT_URL" -Atc "select count(*) from \"$t\""
done
# миграции согласованы
cd backend && DATABASE_URL="$NEW_DIRECT_URL" npx prisma migrate status
```
Также выборочно: последнее сообщение общего чата, пользователь `neskai`, комната кинотеатра.

## 6. Переключение

1. В Render → сервис → **Environment**:
   - `DATABASE_URL` = `NEW_POOLED_URL` (или `NEW_DIRECT_URL`, если пулер не подошёл);
   - `DIRECT_URL` = `NEW_DIRECT_URL` (если используете пулер);
   - `RENDER_REGION` = регион сервиса (для админки);
   - `JWT_SECRET` и остальные **не менять** — пользователи останутся залогиненными, refresh-сессии лежат в БД и перенеслись.
2. **Resume** сервиса. Миграции (`prisma migrate deploy` в `CMD`) пройдут по `DIRECT_URL` — на уже мигрированной БД это ничего не меняет.
3. Проверка: вход в приложение, сообщение в чате, комната кинотеатра, «Отара»; админка → «Процессы»: RTT до БД, регион БД = регион сервера, очередь пула 0.

Если одновременно переносите и **Render-сервис** во Франкфурт: создайте новый сервис из того же репозитория в регионе Frankfurt с теми же переменными окружения, проверьте на его `*.onrender.com`-адресе, затем переключите `NEXT_PUBLIC_API_URL`/домен фронтенда (и `CORS_ORIGIN`, `FRONTEND_URL` при необходимости), старый сервис оставьте приостановленным до конца периода отката.

## 7. Откат

До переключения env — откат не нужен: старая БД не менялась (дамп только читает), просто сделайте **Resume** и ничего не меняйте.

После переключения, если что-то пошло не так:
1. Render → Environment: вернуть прежние `DATABASE_URL` (и убрать `DIRECT_URL`) → сервис перезапустится на старой БД.
2. Данные, записанные уже в новую БД после переключения, в старой отсутствуют. Если откат происходит не сразу, их нужно вручную перенести (дамп отдельных таблиц новой БД → старая) — поэтому окно проверок на шаге 6.3 лучше пройти сразу после Resume и откатываться в первые минуты.
3. **Не удаляйте старый проект Neon минимум 7 дней** после успешного переноса; затем удалите его, чтобы не платить за два.

## 8. После переноса

- Сравнить RTT в админке: ожидается 1–5 мс (до — ~94 мс).
- Снять с сервера лишние перестраховки: при RTT в единицы мс ранее медленные запросы (`joinRoom`, непрочитанные) ускорятся многократно.
- Обновить `backend/.env.example` / переменные на Render (`DATABASE_URL`, `DIRECT_URL`, `RENDER_REGION`).
